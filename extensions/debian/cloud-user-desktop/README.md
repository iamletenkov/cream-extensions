# cloud-user-desktop

Для **вендорского** рабочего стола — такого, который пришёл в базовом образе,
а не расширением `gnome`/`xfce4`/`lxde` (Jetson Nano от Q-engineering,
Raspberry Pi OS): убирает вендорскую учётку и приводит ручки рабочего стола
(расширение `desktop`), чтобы автологин и группы достались пользователю cloud-init.

> **Живая машина — с `--accept-risk`.** Удаляет вендорскую учётку CLOUD_USER_DESKTOP_REMOVE вместе с домашним каталогом (userdel -r — необратимо: учётка и её файлы не восстанавливаются) и снимает автологин gdm3 и LightDM, указывающий на неё; автологин другой учётки не трогается
<!-- /catalog:facts -->

С расширением `gnome`/`xfce4`/`lxde` это расширение не нужно: они тянут `desktop` сами.

## Что делает

- **`install`** — удаляет вендорскую учётку вместе с домашним каталогом, если задано
  её имя. **На сборке, а не на первой загрузке**: иначе образ до первой загрузки
  возит пользователя с известным паролем. Учётки нет — 0 (повтор ничего не делает);
  root и системные учётки (uid < 1000) — отказ; имя проверяется по форме;
  `userdel -r` отказал — повтор без домашнего каталога; учётка осталась (занята
  процессом или сессией) — отказ.
- **Вендорский автологин** на удалённую учётку `install` снимает сам (6.0.0), когда
  учётки уже нет: в gdm3 (`/etc/gdm3/daemon.conf`, `custom.conf`) —
  `AutomaticLogin=<учётка>` с `AutomaticLoginEnable` и `TimedLogin=<учётка>` с
  `TimedLoginEnable`/`TimedLoginDelay`; в LightDM (`lightdm.conf`,
  `lightdm.conf.d/*.conf`) — `autologin-user=<учётка>` с `autologin-user-timeout`, только
  в той секции, где она названа. Автологин **другой** учётки, закомментированный
  ключ, файл-ссылку и файл в каталоге-ссылке (`/etc/gdm3`, `/etc/lightdm`,
  `lightdm.conf.d`; предупреждение) не трогает. Файл заменяется целиком (`mv -T`
  временного рядом), права и владелец переносятся.
  Раньше это делало умолчание `DESKTOP_AUTOLOGIN=0` расширения `desktop` 1.x;
  `desktop` 2.x чужой автологин не трогает. Своей службы у расширения нет:
  ручки рабочего стола — [`desktop`](../desktop/README.md) (`depends`), его
  `configure` на каждой загрузке до менеджера входа вносит пользователя cloud-init
  (библиотека [`cloud-user`](../cloud-user/README.md)) в группы сеанса и пишет
  автологин, если задан `DESKTOP_AUTOLOGIN=1`.
- **`remove`** — ничего не возвращает: удалённая учётка не восстанавливается (смысл
  был в её пароле), ручки принадлежат `desktop`.

## Параметры

<!-- catalog:params -->
| Ключ | Тип | Умолчание | Что задаёт |
|---|---|---|---|
| `CLOUD_USER_DESKTOP_REMOVE` | строка `^[a-z_][a-z0-9_-]{0,31}$` | пусто | вендорская учётка, которую удалить вместе с домашним каталогом (только uid >= 1000); пусто — ничего *(только при установке)* |
<!-- /catalog:params -->

- `CLOUD_USER_DESKTOP_REMOVE` — только имена вида `[a-z_][a-z0-9_-]*` и uid ≥ 1000.
- Ключи `DESKTOP_*` — домен расширения `desktop` (`cream show desktop`), не этого.

## Установка

На машине с подключённым каталогом ([как подключить](../../../docs/getting-started.md)):

```bash
sudo cream install --with-deps --accept-risk cloud-user-desktop CLOUD_USER_DESKTOP_REMOVE=jetson
sudo cream set desktop DESKTOP_AUTOLOGIN=1 DESKTOP_DISABLE_SCREEN_LOCK=1 DESKTOP_DISABLE_SCREEN_BLANK=1
cream show desktop
```

**Обновление — тоже с `--accept-risk`** (`targets.live: confirm` с 6.0.0, `userdel -r`
необратим): `cream upgrade --all` оставит расширение `blocked:risk` (код 68), пока не
сказано явно —

```bash
sudo cream upgrade --all --accept-risk cloud-user-desktop   # обновить осознанно
sudo cream hold cloud-user-desktop                          # или закрепить: --all его пропускает (код 0)
```

Скрипты, которые зовут `cream upgrade --all` без вопроса (cron, агент), выбирают
одно из двух заранее.

В образе bisquite (VMFILE):

```dockerfile
RUN_COMMAND cream install --with-deps cloud-user-desktop CLOUD_USER_DESKTOP_REMOVE=jetson
```

## Этапы

| Когда | Что происходит |
|---|---|
| сборка образа / `cream install` | удаление вендорской учётки, снятие её автологина в gdm3 и LightDM |
| загрузка | своего хука нет; `configure` расширения `desktop` вносит пользователя cloud-init в группы и пишет автологин до менеджера входа |
| `cream remove` | ничего не возвращает |

## Известные ограничения

- **Если seed cloud-init не прочитается, интерактивных учётных записей на
  устройстве не останется** — только `root` с вендорским паролем (см. «Цена,
  названная прямо»).
- На Jetson Nano с вендорским образом не собиралось: платы на стенде нет.

## Подробности

### Зачем

Готовые образы производителей приходят с **предустановленным пользователем
и публично известным паролем**: у Q-engineering для Jetson Nano это
`jetson`/`jetson` (замер 2026-09-06: `passwd -S jetson` отвечает `P`).
Пока учётка в образе, каждое устройство несёт известную всем пару, а автологин
занимает сессию ей, а не пользователю из манифеста записи (на той же плате
`vino-vnc` был настроен для `garage`, а сессию держал `jetson`).

### Цена, названная прямо

**Если seed cloud-init не прочитается, интерактивных учётных записей на
устройстве не останется** — только `root` с вендорским паролем. Пароль `root`
расширение не трогает: снять его значило бы превратить неудачную загрузку
в кирпич. Нужен и он — задайте `root-password` в манифесте записи.

### Почему группы — до менеджера входа

Xorg сессии автологина запускается от имени пользователя, и без `video` он
не открывает GPU: `NVIDIA(GPU-0): Failed to initialize the NVIDIA graphics
device!`, `gdm3: GdmDisplay: Session never registered, failing`. Группы,
внесённые после `cloud-final`, то есть после старта менеджера входа, на первой
загрузке AGX Orin 2026-09-14 проиграли гонку (52 падения Xorg). Поэтому это
`configure` расширения `desktop` — стадия `system` до менеджера входа.
