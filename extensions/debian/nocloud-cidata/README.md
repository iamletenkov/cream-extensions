# nocloud-cidata

Заставляет cloud-init читать NoCloud-seed с раздела, помеченного `cidata`.

```
EXTENSION nocloud-cidata      # образ bisquite (targets.live: no — только сборка)
```

> **С 2.0.0 — cream/v1.** `install.sh` стал хуком `hooks/install`, появился хук
> `remove`; каталог в госте — `/opt/cream/ext/nocloud-cidata/`. Файл переименован:
> `zz-cream-nocloud.cfg` → **`zz-cream-nocloud.cfg`** (в расширении —
> `files/zz-cream-nocloud.cfg`). `cream install` на живой машине отказывает:
> `targets.live: no`.

## Зачем

`bs device write` кладёт seed (`user-data`, `meta-data`, `network-config`) на
отдельный FAT32-раздел с меткой `cidata`. **Штатные образы эту метку не ищут**,
и причины у них разные — замерено на трёх реальных образах для Raspberry Pi
(2026-08-30):

| Образ | cloud-init | Откуда читает seed |
|---|---|---|
| Raspberry Pi OS Trixie | есть | `seedfrom: file:///boot/firmware` |
| Ubuntu 24.04.4 | есть | `fs_label: system-boot` |
| Debian raspi bookworm | **нет** | — |

Механика отказа у первых двух разная, и разница практическая. У Ubuntu метка
**заменяется**, а не дополняется (`DataSourceNoCloud._get_data`:
`label = self.ds_cfg.get("fs_label", "cidata")`) — том `cidata` не сканируется
вовсе. У Pi OS `fs_label` не задан, том **читается и вмерживается**, а следом
`seedfrom` присваивает поверх `user-data`, `vendor-data` и `network-config`,
и наша конфигурация теряется.

Итог одинаков и тих: карта запишется, устройство загрузится — и придёт **без
пользователя, без сети и без SSH-ключей**.

## Подключение

```vmfile
EXTENSION nocloud-cidata
```

Параметров нет.

Единственный обязательный порядок — **после** установки cloud-init, если он
ставится слоем `INSTALL`: без каталога `/etc/cloud/cloud.cfg.d` расширение
отказывает. Относительно прочих слоёв порядок не важен по построению — имя
`zz-` выигрывает у штатных файлов при любом положении слоя (разбор ниже).
Перебить его может только слой, который сам кладёт в `cloud.cfg.d` файл
с лексикографически более старшим именем.

## Манифест

| Поле | Значение |
|---|---|
| `targets` | `build: exec`, `live: no` — cloud-init читает конфигурацию до того, как что-либо могло бы её поправить |
| `platform` | `deb`, `amd64`/`arm64`, `os`: debian, ubuntu |
| `provides` | `nocloud-cidata-seed` |
| `hooks` | `install`, `remove` (по 5 мин) |
| `depends`, `conflicts` | — |

Зависимостей нет, хотя cloud-init обязателен: способности «в образе есть
cloud-init» в дереве не объявляет никто. Поэтому проверка осталась в хуке
`install` — она громкая и называет следствие.

Файл кладёт хук, а не поле `files` манифеста (`build: exec` на машине цели):
отказ без cloud-init должен прийти раньше, чем файл ляжет.

## Что делает

Кладёт `/etc/cloud/cloud.cfg.d/zz-cream-nocloud.cfg`:

```yaml
datasource_list: [ NoCloud, None ]
datasource:
  NoCloud:
    fs_label: cidata
    seedfrom: ""
```

**Имя начинается с `zz-`, а не с `99-`, и это не стиль.** cloud-init сортирует
`cloud.cfg.d` в **обратном** порядке и берёт первый (`util.read_conf_d`),
поэтому имя обязано быть лексикографически старше любого штатного: `z` больше
любой цифры. С префиксом `99-` штатный `99_raspberry-pi.cfg` оказался бы
равноправным, и порядок решал бы случай.

Файл ставится `install -m 0644` и перезаписывается при каждом прогоне, так
что повторная сборка по уже обработанному образу безопасна.

## Отказы

**Нет `/etc/cloud/cloud.cfg.d`** — отказ, а не предупреждение. Без cloud-init
файл не читает никто, и расширение изобразило бы работу; обнаружилось бы это
на устройстве, после `dd`, по отсутствию пользователя. Ставьте cloud-init
слоем `INSTALL` до этого расширения.

Если рядом нашёлся штатный конфиг с `seedfrom` или `fs_label`, установка
говорит об этом предупреждением: следующий читатель журнала иначе не свяжет
исчезновение штатного источника seed с этим расширением.

Предупреждение неполное, и знать об этом стоит: ищутся только файлы
`*raspberry*.cfg` и `*ubuntu*.cfg`. Штатный конфиг с другим именем будет
перекрыт так же молча — работать расширение будет по-прежнему правильно,
но в журнале про перекрытие ничего не скажет.

## `remove`

Удаляет `/etc/cloud/cloud.cfg.d/zz-cream-nocloud.cfg`; штатные конфиги источника
seed снова действуют.

## Ограничения

`build: exec`, то есть архитектуры хоста и образа обязаны совпасть —
libguestfs не выполняет код в госте чужой архитектуры. Само копирование файла
архитектуры не касается; ограничение вносит форма расширения, а не задача.

## Проверки

- **V** — `make cream-validate`, `tools/check-names.sh`.
- **H** — `tests/test-nocloud-cidata.sh`: файл байт в байт и 0644, YAML, имя старше
  штатных, повтор, предупреждение о перекрытом конфиге, отказ без cloud-init, `remove`.
- **P** — сборка образа через bisquite (живого прогона нет: `live: no`).

### Вручную

На собранном образе:

```console
$ virt-cat -a образ.qcow2 /etc/cloud/cloud.cfg.d/zz-cream-nocloud.cfg
```

На устройстве после первой загрузки:

```console
$ cloud-init query --all | grep -i datasource
$ ls /var/lib/cloud/seed/
```
