# x11vnc

VNC-доступ к рабочему столу X11 пользователя сеанса (`X11VNC_USER`, пусто — пользователь
cloud-init). Сервер — системный юнит-шаблон `x11vnc@<пользователь>.service`, по умолчанию
слушает только петлю (доступ — SSH-туннелем).

**Чей экран и какой дисплей** (6.0.0). Пользователь — `X11VNC_USER`, пусто —
пользователь cloud-init (как раньше); только учётка с uid **1000..65533**: root,
`gdm`, `lightdm` и другие системные — отказ, код 78 (у `gdm` authority — экрана
входа). Дисплей — `X11VNC_DISPLAY=auto` (умолчание): X11-сеанс пользователя на
seat0 по logind, иначе его Xorg, иначе `:0`. Найденный без logind дисплей `:N` —
только X-сервера, который доказан: доверенный lock-файл `/tmp/.X<N>-lock` хранит pid
Xorg, оба слушателя `X<N>` (файл и абстрактный — xcb идёт к нему первым) — fd этого
Xorg, у `:0` ещё процесс и сокет — root или пользователя; fd Xorg root обёртке не
видны — такой дисплей только через logind (см. «Известные ограничения»). Дисплей ещё подтверждает собственная
authority пользователя — по `unix:N`, без отката на TCP ([`lib/x-session.sh`](../../../lib/x-session.sh)); `:N` — жёстко, сохранённое
`:0` прежних версий остаётся как есть. Стол, поставленный не через cream (готовая
Ubuntu, GDM/LightDM/SDDM), — [`existing-desktop`](../existing-desktop/README.md); сеанс
на Wayland не показывается — [`gdm-xorg`](../gdm-xorg/README.md).

## Что делает

- **`install`** — на живой машине сначала проверка: нет Xorg (`/usr/lib/xorg/Xorg`,
  `/usr/bin/Xorg`) или включённого менеджера входа (ссылка `display-manager.service` на
  существующий юнит; замаскированный — ссылка на `/dev/null` — не включён) — код 20 (cream 68) с текстом «нет X-сервера / менеджера входа:
  поставьте стол или `existing-desktop`», ничего не поставлено; при сборке образа
  проверки нет (стол может прийти той же сборкой). Затем `x11vnc`, `xauth`, `x11-utils`
  (обёртке нужен `xdpyinfo`, у x11vnc он лишь в Recommends), `x11-xserver-utils`
  (`xhost` — запасной путь поиска дисплея без logind), `openssl`; удаляет прежний
  `/etc/default/bisquite-x11vnc`.
  Юнит `files/x11vnc@.service` → `/etc/systemd/system/x11vnc@.service` кладёт
  cream (поле `files`).
- **`configure`** (каждая загрузка, стадия `graphical`, после
  `display-manager.service`), по порядку:
  1. `X11VNC_DISPLAY` не `auto` и не `:N` — сбой (1);
  2. на живой машине нет Xorg или включённого менеджера входа — экземпляры гасятся,
     код 1 (текст тот же, что у `install`);
  3. `X11VNC_USER` задан, но не учётка с uid 1000..65533 — экземпляры гасятся, код 78;
  4. пусто — пользователь cloud-init (на загрузке ждёт до 30 с); нет его или uid вне
     1000..65533 — предупреждение, экземпляры (например, от снятого `X11VNC_USER`)
     гасятся, код 0;
  5. файл пароля из секрета (см. «Пароль: производный файл»);
  6. `x11vnc@<пользователь>` включается, экземпляры прежних пользователей гасятся;
     менеджер входа включён, но не запущен (сразу после стола, до перезагрузки) —
     предупреждение «менеджер входа не запущен», экземпляр без перезапуска (иначе
     `Requires=` поднял бы менеджер входа), код 0; иначе — строка диагноза seat0
     («на seat0 сеанс bob (x11), x11vnc ждёт alice: sudo cream set x11vnc
     X11VNC_USER=bob», Wayland, экран входа) и перезапуск (`--no-block`).
- **`apply`** (после `cream set`) — то же, не дожидаясь пользователя; экземпляр
  перезапускается.
- **`remove`** — экземпляры выключены, файл пароля и маркер сняты; пакет `x11vnc` —
  только если его поставил этот `install`, после симуляции apt (`apt-guard`): если apt
  снял бы что-то кроме `x11vnc` — отказ (1) до любых изменений.

Требование родовое — любой X-сервер, любой менеджер входа: путь к X authority ищется
в рантайме (см. «Как находится X authority»). Рабочий стол (`gnome`, `xfce4`, `lxde`)
ставится раньше (готовый стол — `existing-desktop`), автологин — `cream set desktop
DESKTOP_AUTOLOGIN=1`: без сессии пользователя серверу не к чему подключаться.

Нет пользователя cloud-init — предупреждение и 0: файл строится без владельца, сервер не
включается.

Обёртка `files/run-x11vnc.sh` (юнит, `User=%i`): решение о пароле — первым; uid
экземпляра 1000..65533, иначе 78 — до обращения к logind и X; `X11VNC_DISPLAY` не
`auto`/`:N` — 78; ждёт X-сеанс пользователя (строка и диагноз seat0 раз в 5 минут, не
цикл перезапусков); Wayland — 78 и подсказка про `gdm-xorg`. `x11vnc` запускается без
`-loop`: конец X-сеанса завершает его, юнит (`Restart=always`, кроме 78) запускает
обёртку снова, и она находит новый сеанс — после выхода и входа он может оказаться на
другом дисплее.

## Параметры

<!-- catalog:params -->
| Ключ | Тип | Умолчание | Что задаёт |
|---|---|---|---|
| `X11VNC_PORT` | `port` | `5900` | порт RFB |
| `X11VNC_USER` | строка `^[a-z_][a-z0-9_-]{0,31}$` | пусто | чей X-сеанс показывать; пусто — пользователь cloud-init; uid только 1000..65533, иначе отказ (код 78) |
| `X11VNC_DISPLAY` | строка `^(auto\|:[0-9]+(\.[0-9]+)?)$` | `auto` | auto (и пусто) — дисплей X-сеанса пользователя на seat0 (logind, его Xorg, :0); :N — жёстко |
| `X11VNC_LISTEN` | `localhost` \| `all` | `localhost` | localhost — только петля (доступ ssh-туннелем), all — все интерфейсы |
| `X11VNC_PASSWORD` | `str` | пусто | пароль VNC (значимы первые 8 символов); пусто — сервер выключен; задаётся только через stdin: cream set x11vnc X11VNC_PASSWORD=- *(секрет: `KEY=-` со stdin или `--params-file`, не в argv)* |
| `X11VNC_ALLOW_NO_PASSWORD` | `bool` | `0` | 1 — разрешить сервер без пароля при пустом X11VNC_PASSWORD, только с X11VNC_LISTEN=localhost (предупреждение при каждом configure и старте; с all — отказ, код 78); 0 — без пароля сервер выключен |
<!-- /catalog:params -->

Домен `x11vnc`: настройки — `/etc/cream/x11vnc/config`, пароль — в
`/etc/cream/x11vnc/secrets`. Пароль задаётся только со stdin: в argv секрет cream
не примет. Значимы первые 8 символов пароля (так устроена VNC-аутентификация).

```bash
echo 'пароль' | sudo cream set x11vnc X11VNC_PASSWORD=-
sudo cream set x11vnc X11VNC_LISTEN=all
```

## Установка

На машине с подключённым каталогом ([как подключить](../../../docs/getting-started.md)),
после рабочего стола:

```bash
sudo cream install --with-deps x11vnc
echo 'пароль' | sudo cream set x11vnc X11VNC_PASSWORD=-
cream show x11vnc
```

На готовой машине со своим столом (Ubuntu с GDM, LightDM, SDDM):

```bash
sudo cream install --with-deps existing-desktop gdm-xorg   # gdm-xorg — только для GDM
sudo cream install --with-deps x11vnc
sudo cream set x11vnc X11VNC_USER=<кто входит на экран>    # если не пользователь cloud-init
```

`pixelflux-tegra`, `vino-vnc` и `wallpaper` пользователя берут по-прежнему из
`cloud-user` (Jetson Nano: группа `video`) — `X11VNC_USER` на них не влияет.

В образе bisquite (VMFILE):

```dockerfile
RUN_COMMAND cream install --with-deps desktop DESKTOP_AUTOLOGIN=1
RUN_COMMAND cream install --with-deps gnome
RUN_COMMAND cream install --with-deps x11vnc X11VNC_PORT=5901
```

Пароль — не литералом в VMFILE (VMFILE едет в образ), а на машине:
`echo 'пароль' | sudo cream set x11vnc X11VNC_PASSWORD=-`.

## Известные ограничения

- **Xorg от root при пустом `Display` в logind — обёртка ждёт** (GDM через
  `Xorg.wrap`: нет KMS, NVIDIA без `nvidia-drm.modeset=1`; `startx` от root): fd такого
  Xorg обёртке, работающей от пользователя, не видны, дисплей не доказать. Обход —
  сознательно `sudo cream set x11vnc X11VNC_DISPLAY=:N`.
- **Жёсткий `X11VNC_DISPLAY=:N` и `Display` из logind — без привязки к Xorg** (как в
  5.x; authority проверяется по `unix:N`): на `:N` без X-сервера wild-cookie GDM получит тот, кто
  займёт `@/tmp/.X11-unix/X<N>`. Жёсткий `:N` — только там, где на нём гарантированно
  X-сервер пользователя. Оба пункта —
  [#139](https://github.com/iamletenkov/cream-extensions/issues/139),
  [known-issues](../../../docs/known-issues.md).
- Только X11: на Wayland-сессии бесполезен (см. «Wayland»); GDM — с `gdm-xorg`.
- Только учётки с uid 1000..65533: экран входа (`gdm`, `lightdm`) не показывается.
- Пустой пароль — сервер **выключен**; без пароля — только явным
  `X11VNC_ALLOW_NO_PASSWORD=1` и только на петле (решение владельца 2026-11-12):
  с `X11VNC_LISTEN=all` configure выключает и гасит экземпляры, код 78, обёртка — тоже 78.
- Сессии в контейнере нет — включение сервера пользователю проверяет только H.

## Подробности

### Пароль: производный файл

`configure` (на каждой загрузке и после `cream set` — хук `apply`) строит из секрета
`/etc/x11vnc/passwd` в формате `-rfbauth`: пароль, зашифрованный DES с постоянным
общеизвестным ключом, — то есть файл и есть пароль. Поэтому:

- пароль читается `cream config get --secret` в переменную оболочки и уходит только
  через канал: `x11vnc -storepasswd` берёт пароль лишь аргументом, и файл строит
  `openssl enc -des-ecb` со stdin — байт в байт то же (сверено с `x11vnc -storepasswd`
  на Debian 12, Ubuntu 22.04 и 24.04). Пароля нет в `ps`, журнале и окружении
  дочерних процессов; юнит сервера читает только `config`, не `secrets`;
- файл рождается под `umask 077` в корневом `/etc/x11vnc` (0755 — пользователь проходит
  к файлу), отдаётся пользователю сессии (`hand_over_passfile`, 0600) и переименовывается
  на место: окна с широкими правами нет. Ссылка на месте файла или каталога, каталог не
  root — отказ;
- повтор с тем же паролем файл не переписывает;
- **fail-closed**: пустой пароль — свой файл снят, сервер **выключен** («пароль не задан —
  x11vnc выключен»). Без пароля — только явным `X11VNC_ALLOW_NO_PASSWORD=1`: тогда
  `configure` ставит производный маркер `/etc/x11vnc/nopw` — заново, не по ссылке (и снимает его во
  всех прочих случаях — маркер руками не переживёт configure), а обёртка поднимает
  `-nopw` только при маркере **и** ключе, с предупреждением при каждом старте. Нет ни
  файла, ни разрешения, или файл не читается — отказ запуска, код 78 (юнит не крутит
  перезапуски, `configure` поднимает экземпляр сам);
- файл пароля, построенный не этим configure (например, унаследованный от прежней
  установки), при пустом секрете не удаляется и не используется: сервер выключен, в
  журнале — как перенести пароль (`echo 'пароль' | sudo cream set x11vnc
  X11VNC_PASSWORD=-`); `remove` его тоже не трогает;
- не построился файл — сбой `configure` (маркер снят заранее), никогда не `-nopw`.

### Как находится X authority

Путь к authority **не зашит в юните**, а ищется в рантайме обёрткой
`run-x11vnc.sh`. Зашитый путь

```
-auth /var/run/lightdm/%i/:0
```

не работает **ни под одним** дисплей-менеджером. Это склейка двух разных схем
LightDM (проверено по исходникам, версии 1.2–1.32 — одинаково):

- `src/x-server-local.c` пишет `<run-dir>/**root**/:0` — authority самого
  X-сервера, владелец root, права 0600, пользователю недоступен. Отсюда
  и взялось имя файла `:0`;
- `src/session.c` даёт пользователю `~/.Xauthority` (умолчание) либо
  `<run-dir>/<user>/xauthority` при `user-authority-in-system-dir=true`.

Под GDM ≥ 42 файл лежит в третьем месте — `/run/user/<uid>/gdm/Xauthority`
(`gdm/daemon/gdm-x-session.c`).

С 6.0.0 дисплей и authority ищет общая библиотека
[`lib/x-session.sh`](../../../lib/x-session.sh) (`xs_find_display`, `xs_find_authority`;
в дереве расширения — `files/x-session.sh`). Кандидаты authority — в порядке убывания
надёжности, берётся первый, на котором сработал `xdpyinfo`:

1. `~/.Xauthority` пользователя (LightDM, `session.c`);
2. `/run/user/<uid>/gdm/Xauthority` (GDM ≥ 42);
3. `/run/lightdm/<user>/xauthority` (LightDM при
   `user-authority-in-system-dir=true`);
4. значение `-auth` из командной строки живого `Xorg` (читается
   из `/proc/<pid>/cmdline`) — тот, кто запустил сервер, знает путь точно;
5. legacy-раскладка GDM `/run/gdm3/auth-for-<user>-*/database` — последней,
   на современных сборках её нет.

Перед этим списком обёртка пробует `$XAUTHORITY`, если он задан, — но
в окружении системного юнита его нет, поэтому нумерация выше и нумерация
в замерах ниже совпадают.

Не подошёл ни один — **громкий отказ с перечислением всех проверенных путей**
и пометкой, какие из них существуют.

**`x11vnc -auth guess` не годится.** Его встроенный скрипт FINDDISPLAY
перебирает `~/.Xauthority`, `/tmp/.gdm*`, `/tmp/.Xauth*` и глобы
`/var/run/gdm*/auth-for-*/database` и `auth-cookie-*` — пути GDM ≥ 42 там
нет, а `auth-for-*` это legacy-раскладка. Плюс `man x11vnc` предупреждает,
что FINDDISPLAY зависает навсегда, если гритер держит X-сервер.

### Wayland

`x11vnc` обслуживает X11 и на Wayland-сессии бесполезен. Обёртка спрашивает
у logind тип сеанса пользователя на seat0 (`lib/x-session.sh`) и отказывает внятно — кодом 78 (EX_CONFIG): юнит
(`RestartPreventExitStatus=78`) не перезапускает её каждые 5 с. После
перехода на Xorg и нового входа — `sudo systemctl restart x11vnc@<пользователь>`
(или перезагрузка: configure запускает экземпляр сам).

Проверять наличие сокета `/tmp/.X11-unix/X0` для этого **нельзя**: под Wayland
его создаёт mutter для Xwayland, он там есть. Собственная защита `x11vnc`
тоже не сработает — она смотрит на `$WAYLAND_DISPLAY`, которого в окружении
системного юнита нет.

Xorg у GDM включает [`gdm-xorg`](../gdm-xorg/README.md) (стол не через cream) или
расширение `gnome` (`WaylandEnable=false`).

### Диагностика

```bash
cream show x11vnc
systemctl status cream-configure@x11vnc
systemctl list-units 'x11vnc@*'; journalctl -u 'x11vnc@*' -b | tail -30   # строка «дисплей …, authority …», диагноз seat0
ls -l /etc/x11vnc/; ss -ltnp | grep 5900
```

здесь не помог бы.
